## Decision

Use `qualitative_coding` as the first ordinary Brian-owned project to exercise
automatic outcome admission. Run one maintenance-only pilot in an isolated
linked worktree at exact baseline
`785e4d69ab8de29ace8b021fdded6dbf1d22b318`. Do not choose QC's next product
feature, unpause a model evaluation, deploy, or alter a researcher-visible
analysis result.

authoritative Project Graph ID is `qualitative_coding`, while the accepted

Inventing a hyphenated alias would break exact authority. Plan #124 therefore
first separates Project Graph project-ID validation from outcome/lineage slug
validation and proves the real QC identity through the portfolio boundary.

After that prerequisite merges, the pilot installs the already-accepted Plan
#123 owners through existing bounded delivery commands where available,
declares the few pilot-only wrapper files as visible exceptions, activates
ordinary and selected admission in QC, and proves one complete lifecycle:

1. create the QC plan, graph, scenario, allocation input, claim, and worktree
   before activation;
2. allocate and select an exact Project Graph-bound QC maintenance outcome;
3. install and activate the QC consumer;
4. show flagless Make heartbeat and native Codex pre-write both admit active
   exact work;
5. show a sanctioned new-Plan bootstrap remains usable;
6. park the QC allocation and show the same heartbeat and ordinary-authorized
   write deny before mutation; and
7. retain rollback, both-sign receipts, and unchanged product checks.

This plan owns the cross-repository design and promotion decision. The QC
repository owns its local implementation plan and evidence.

## Research

The decision is grounded in pinned local authority, direct Git state, accepted
Plan #123 evidence, and authentic contract execution. External landscape
research is not needed for this maintenance/adoption boundary: the relevant
question is whether the repository's own typed contract and installed commands
can represent and enforce its authoritative identity. Research stops at the
first exact compatible portfolio resolution plus one authentic QC lifecycle;
broader installer or fleet comparisons are explicitly downstream.

## Gap

Plan #123 proves automatic admission only inside the framework repository.
That does not show that an ordinary project can bootstrap, work, close, and
recover without an optional flag or framework-source import. Worse, the first
ordinary target's canonical ID is currently unrepresentable by the accepted
contract. Until both gaps are closed, an agent can still evade the intended
ecosystem policy by staying on uninstalled commands or by substituting an
unreviewed project alias.

## User Outcome

Brian can start or continue a real, complex project without remembering a
special outcome flag. Approval text, willingness to spend, and elapsed time do
not keep the lane writable after its exact allocation or continuation state
stops permitting work. At the same time, an honest new plan can still start
through one narrow bootstrap rather than requiring an unsafe bypass.

## Canonical Behavioral Example

**Starting state:** A QC linked worktree has an exact live claim, tracker,
selected maintenance scenario, active allocation, and config values
`prewrite_mode: enforce` plus `outcome_admission_mode: enforce_selected`. The
operator says "I approve, continue" and cost telemetry is arbitrarily high.
The caller supplies no outcome flag.

**Action:** Run the installed Make heartbeat and the installed Codex pre-write
hook payload against `meta-process.yaml`.

**Expected result:** Active exact state returns zero and appends outcome plus
ordinary receipts. After the exact allocation is parked, the same commands
return nonzero with `portfolio_allocation_inactive`; claim heartbeat and target
bytes are unchanged.

**Failure signal:** The caller can omit the gate; ordinary denial is revived;
the installed command imports from Enforced Planning rather than QC; a new
Plan bootstrap deadlocks; a second contract-scoped file falsely blocks;
parking does not stop the lane; product behavior changes; or another
repository/config/hook is mutated.

## Stable Product Control

The pilot changes governance only. Preserve QC's canonical product state and
run the cheapest existing checks that can invalidate accidental product
impact. At minimum:

- `make docs-check` or the repository's exact equivalent for changed docs;
- import/CLI smoke for the installed governance entrypoints; and
- a focused existing no-provider test or startup check covering the stable
  `/public` or workspace surface if installation touches shared Python import
  paths.

Do not run live LLM E2E, deploy, reset user projects, or change current product
direction for this pilot.

## Failure Behavior

- Missing/malformed config, missing selection, stale claim projection,
  inactive/mismatched allocation, stalled/terminal continuation, or receipt
  failure returns nonzero visibly.
- Ordinary claim denial remains denial without selected resolution.
- Only the uniquely resolved Plan-numbered bootstrap claim may write before
  selection; source/product smuggling denies before worktree creation.
- An out-of-contract target denies even if the ordinary claim includes it.
- Denial does not change claim heartbeat, tracker selection, or target bytes.
- Any installer action outside the frozen pilot manifest stops the pilot for
  reconciliation rather than silently expanding scope.

## Rollback

Before activation, retain the QC baseline revision, the activation commit, and
config/hook/Make digests. Rollback is a recoverable Git revert of the activation
commit or a claimed change setting the YAML string
`outcome_admission_mode: "off"` and restoring the prior ordinary pre-write
mode. Because parking intentionally blocks later source edits, the exact remote
activation commit is the recovery ref for a clean-clone Git revert. No database,
deployment, release, or user-data rollback is part of this pilot.
